## Context

See proposal.md for motivation. Standalone source skills are Markdown files under `skills/`. The coordinator and twelve specialist instructions now live under root-level `subagents/`. Both installers package the coordinator as one skill with specialist references; regular skills retain their existing per-skill layout and Codex UI metadata. Other run artifacts already use `.clanker` and `YYYY-MM-DD`. OpenSpec is initialized with the spec-driven schema and there are no existing capability specs.

The app exposes native subagent tools with model and effort overrides. The standalone CLI currently rejects the user's `service_tier = "priority"`; this change must not depend on a nested CLI review or change that unrelated setting.

## Goals / Non-Goals

**Goals:** Portable coordinator and specialist instructions, inspectable task routing, OpenSpec continuity, and a session audit file that survives follow-ups. Role contracts must make useful delegation possible with minimal worker context.

**Non-Goals:** Custom agent TOML profiles, new agent framework, unrelated installer redesign, global model configuration changes, automatic deployment, logging backend, or automatic commits/archival.

## Decisions

1. **Bundle specialist instructions behind one entry point.** Keep routing, model selection, OpenSpec state, and logging in `subagents/clanker-orchestration-nation.md`; keep twelve separate domain instruction files alongside it. Both installers copy the coordinator to `skills/clanker-orchestration-nation/SKILL.md` and specialists to its `references/<role-name>.md`. References have no separate `SKILL.md` or UI metadata and do not add specialist skill entries. Reuse the existing separately installed `clanker-code-review` for code/security review. Resolve specialists relative to the loaded coordinator (source siblings or installed references), verify their names, and require workers to read their actual paths. Do not fall back to stale standalone copies. Native TOML/Claude agent profiles remain outside scope; native workers receive the selected instructions and dynamic model/effort per assignment.
2. **Preserve parent choice and choose workers by phase.** The user-selected session model and effort remain the orchestrator settings. Astra or Fable may be suggested where available, but another parent choice requires no approval and does not block work. This skill does not switch the parent model or effort; unknown effective settings remain unknown. Sol plans and reviews; Terra implements and executes bounded tests by default. Worker effort defaults are medium for routine work and high for architecture, complex logic, data/security risk, and review. Explicit user choices prevail. Parent choice does not guarantee worker capability: if the runtime cannot honor a worker selection, disclose it and request direction for a substitute rather than silently changing policy.
3. **Use focused worker context and explicit ownership.** On the current collaboration API, model/effort overrides require `fork_turns: "none"` or a bounded positive history count; full-history forks inherit settings. Every prompt carries repository path, actual OpenSpec artifact paths, scope, file ownership, constraints, verification, and expected response. Parent owns shared artifacts; independent writers get disjoint files. Use up to three workers and respect any lower runtime limit.
4. **Use OpenSpec's reported paths and state.** Prefer installed OpenSpec workflows, preserving their authorization boundaries. Meaningful new features require a selected or newly scoped change; small fixes may use a logged lightweight path. Planning workers return content for the parent to incorporate; implementation workers never mark task checkboxes. Reuse active Clanker skills, including the OpenSpec-aware code review, and exclude deprecated legacy workflows.
5. **Append readable events to one daily file.** Use `.clanker/YYYY-MM-DD-orchestration-nation.md` in the target repository. Run identity is a start timestamp with timezone plus known session ID or a checked ordinal. Each appended event includes run ID and event identity; assignment events also identify the specialist skill path actually used. Read before append, use append operations rather than replacing a loaded snapshot, and retain the original run-start file across midnight. The parent writes; workers return summaries. This is an instruction-driven audit trail, not a transactional logging service.
6. **Validate packaging and migration in isolation.** Redirect every installer destination into temporary directories. Exercise fresh installs, upgrade from standalone specialist skills, preservation of custom content and unrelated skills, backup-name collisions, and repeat runs for both PowerShell and Bash where available. Validate the coordinator, specialist frontmatter, catalog resolution, exact copies, and generated Codex metadata. Check that only the coordinator is discoverable from this bundle. Report platform or live-client limits explicitly.

7. **Review rendered UI separately from design and implementation.** Add `clanker-ui-ux-reviewer` as a Sol review role. Its inputs include the running application, design/acceptance context, target routes and viewports, and owned evidence locations. It must view actual rendered captures, exercise relevant interactions, and distinguish verified defects from preferences and untested states. Source-only inspection cannot pass visual acceptance. Serialize shared browser state and review a stable integrated build; assign fixes to the implementer and recheck affected states. An unavailable application or visual tool produces partial/blocked coverage, not a fabricated pass.

## Risks / Trade-offs

- Instructions are not an enforced scheduler or filesystem permission boundary -> verify real tool calls, keep ownership explicit, and review resulting files.
- Fixed custom-agent settings could defeat requested effort -> use generic native workers and explicit settings; log observable mismatches.
- Concurrent sessions share a daily file -> append complete run-attributed event blocks, never rewrite previous entries, and report write failures. Cross-process transactional logging is outside this first version.
- Workflow overhead on trivial edits -> select the smallest useful team and record skipped delegation.
- Model availability and permissions vary -> preflight current tools and preserve existing approval requirements; never claim an unavailable model was used.
- Abrupt process termination can prevent final logging -> reconcile pending entries from observed state on resume rather than assuming success.

## Migration Plan

Move the coordinator and twelve specialists from `skills/` to `subagents/`; leave shared code-review and unrelated standalone skills in place. On the next normal wrangle installation, create the one-skill bundle first, then move old standalone specialist directories identified by current source names into `<agent-root>/backups/orchestration-nation/`. Preserve their complete content and choose unused numbered backup names instead of overwriting earlier backups. A repeat run with no standalone leftovers creates no further backups. Validate resolved paths before directory moves; never delete customized specialist content or migrate unrelated skills. Global installation remains a separate user action; this task tests temporary destinations only. Keep the OpenSpec change active rather than automatically archiving it.
